## Context

Workspace Provisioning receives RunPod serverless template observations through provider-neutral `EndpointTemplateObservation` values. Those observations currently carry the RunPod template runtime environment map into `RunPodEndpointTemplateSnapshot`, which is persisted as Workspace Catalog metadata and exported through generated Workspace command bindings.

That path makes provider-returned template environment values part of the durable and React-visible Workspace contract. Even when the current template env is generated by LumaForge, RunPod may later echo provider-owned values, user-added operator values, or secret-like entries. The Native Layer already owns Provider API Keys and Provisioner Worker bearer tokens behind secure storage; template env values need the same defensive treatment at the persistence and command boundary.

## Goals / Non-Goals

**Goals:**

- Remove `runtime_env` from persisted RunPod endpoint template snapshots.
- Remove `runtime_env` from generated Workspace command DTOs and TypeScript bindings.
- Preserve template reuse, observation, endpoint creation, readiness validation, and cleanup with safe metadata: template id, image ref, mount path, and provider status.
- Keep provider implementation code free to inspect template env only as transient observation data when matching provider resources, without persisting or returning the values.
- Maintain backward compatibility for existing Workspace Catalog records that already contain `runtime_env`.

**Non-Goals:**

- Do not expose redacted environment key names or values to React.
- Do not add a new environment allowlist unless implementation discovers a concrete non-secret UI requirement.
- Do not change RunPod template creation inputs or Endpoint Worker runtime env behavior except where needed to prevent persistence and command exposure.
- Do not implement full Workspace Resource Cleanup.

## Decisions

### Decision: Drop runtime env from the domain snapshot

`RunPodEndpointTemplateSnapshot` should contain only metadata needed for lifecycle continuation and cleanup. The current matching logic already relies on provider status, endpoint worker image ref, mount path, and template id; it does not need persisted env values to determine whether a template can be reused.

Alternative considered: keep the map with redacted values. That still makes provider env key names part of the frontend and persistence contract, and key names can reveal implementation details or secret categories.

### Decision: Treat provider template env as transient provider observation data

Provider-facing observation structs may keep runtime env while provider matching needs it, but the conversion into domain snapshots must discard the map. If matching does not require env equality, the provider-neutral observation should remove `runtime_env` entirely as part of implementation.

Alternative considered: reject non-empty runtime env from RunPod observations. That would break adoption or refresh of valid templates if RunPod echoes env values by default, and it is not necessary once persistence and command responses discard the data.

### Decision: Tolerate legacy persisted `runtime_env`

Existing Workspace metadata may deserialize records containing `runtime_env`. The migration path should remove the field from the Rust snapshot while relying on serde's default behavior of ignoring unknown fields. Any later write of the Workspace should serialize the safe shape without the map.

Alternative considered: add an explicit catalog migration. That is unnecessary if old records deserialize cleanly and are naturally rewritten without the removed field.

### Decision: Make the command contract intentionally smaller

The command-owned remote Specta type for `RunPodEndpointTemplateSnapshot` should remove the runtime env field so generated TypeScript bindings cannot expose provider template env. This is a breaking generated binding shape change, but it is a security fix and the field should not have been frontend-visible.

Alternative considered: keep the TypeScript field as an empty object. That preserves a misleading contract and invites future frontend dependence on a value that must remain native-only.

## Risks / Trade-offs

- Existing frontend code may read `runtime_env` from Workspace metadata -> Update generated bindings and remove any frontend references; the absence is intentional.
- Provider matching might currently depend on env values in a lower layer -> Keep env handling inside the provider boundary or replace it with a safe boolean/fingerprint that is never persisted or returned.
- Legacy records might require deserialization care -> Verify catalog tests with old JSON containing `runtime_env` and ensure subsequent snapshots omit it.
- Tests may lose direct env assertions -> Replace them with assertions that secret-like env values do not appear in persisted Workspace snapshots or command-facing DTOs.

## Migration Plan

1. Remove `runtime_env` from `RunPodEndpointTemplateSnapshot` and command-owned remote binding metadata.
2. Update provisioning snapshot conversion to discard provider-returned env before persistence.
3. Update provider-neutral observations only if env is no longer needed outside provider-local matching.
4. Regenerate frontend command bindings if the project requires generated artifacts to be committed.
5. Update tests and fixtures so legacy input with `runtime_env` deserializes, while new persisted and command-facing snapshots omit the field.

Rollback should be avoided because reintroducing persisted template env would restore the secret exposure path. If implementation discovers a real env-derived lifecycle need, store a native-only safe compliance flag or fingerprint instead of env names or values.
